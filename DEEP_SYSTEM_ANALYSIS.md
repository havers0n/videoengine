## 1. РЕКОНСТРУКЦИЯ НАМЕРЕНИЯ (INTENT)

### Основная проблема

Система решает проблему **генерации детерминированных анимационных движков через LLM (Gemini)** с последующей автоматической оценкой их "стабильности" через статический анализ кода.

### Гипотеза исследования

**Гипотеза**: Можно научить LLM генерировать стабильные (детерминированные) анимационные движки, используя:
1. Статический AST-анализ для выявления паттернов стабильности
2. Статистический анализ (Lift) для обратной связи в промпты
3. Rule-based классификацию для автоматической категоризации

**Подразумеваемая гипотеза**: Статические паттерны кода (наличие `fixed_timestep`, `deterministic_rng`, отсутствие `setState_in_raf`) коррелируют с фактической детерминированностью на runtime.

### Тип системы

Это **экспериментальная исследовательская система** (research artifact), которая эволюционирует в:
- **Инструмент для генерации промптов** (prompt engineering tool)
- **Фреймворк для статического анализа сгенерированного кода** (static analysis framework)
- **Систему обратной связи для LLM** (feedback loop system)

**НЕ является**:
- Production-ready продуктом
- Runtime-тестирующей системой
- Полноценным валидатором детерминированности

## 2. АРХИТЕКТУРА СИСТЕМЫ

### Основные подсистемы

#### 2.1. Pipeline ингеста (`scripts/ingest.mjs`)

**Роль**: Обработка новых прогонов генерации

**Поток данных**:
```
zip-файлы → extracted/ → variants/ → analysis → reports/ → master/dataset.json
```

**Ключевые решения**:
- Run-based организация (каждый прогон = отдельный артефакт)
- Нормализация структуры вариантов (поиск App.tsx/main.tsx)
- Маппинг промптов к вариантам (mapping.json)

**Сильные стороны**:
- ✅ Четкая изоляция runs
- ✅ Возможность отслеживания эволюции промптов
- ✅ Автоматическая нормализация

**Слабые стороны**:
- ⚠️ Нет валидации структуры zip-файлов
- ⚠️ Нет дедупликации по содержимому на этапе ингеста

#### 2.2. AST-анализатор (`scripts/analyze-variants.mjs`)

**Роль**: Статический анализ TypeScript/TSX кода для извлечения признаков (features)

**Технология**: `ts-morph` (TypeScript AST parser)

**Извлекаемые признаки**:
- **Архитектурные**: `has_raf`, `has_canvas_2d`, `has_stateRef`, `setState_in_raf`
- **Физика**: `has_fixed_timestep`, `has_deterministic_rng`, `uses_performance_now`
- **Визуальные**: `has_clusters`, `has_threads`, `has_trails`, `has_gradients`
- **Силы**: `force_spring`, `force_damping_mul`, `force_noise_jitter`

**Методы детекции**:
1. **Regex-паттерны**: Быстрая детекция простых паттернов
2. **AST-анализ**: Точная детекция вызовов функций, типов
3. **Контекстный анализ**: Поиск паттернов в определенных контекстах (например, внутри RAF loop)

**Сильные стороны**:
- ✅ Детальная детекция (feature_events с номерами строк)
- ✅ Комбинация regex + AST для баланса скорости/точности
- ✅ Логирование всех найденных паттернов

**Слабые стороны**:
- ⚠️ Нет проверки контекста использования (например, `Math.random()` может быть в инициализации, а не в loop)
- ⚠️ Нет анализа потока данных (data flow analysis)
- ⚠️ Нет проверки семантики (например, `force_noise_jitter` может использовать несидированный рандом)

#### 2.3. Классификатор (`classifyEngineClass`)

**Роль**: Категоризация вариантов по "стабильности"

**Классы**:
1. **INVALID**: `setState_in_raf === true` (критическое нарушение)
2. **NON_DETERMINISTIC**: `uses_date_now` ИЛИ (`uses_math_random` И `!has_deterministic_rng`)
3. **NON_COMPLIANT**: `!has_fixed_timestep` (абсолютный gatekeeper)
4. **STABLE**: `has_fixed_timestep` И (`uses_performance_now` ИЛИ `has_deterministic_rng` ИЛИ `has_stateRef`) И `!setState_in_raf`
5. **SEMI**: `uses_performance_now` ИЛИ `uses_ts_from_raf` (без fixed timestep)
6. **CHAOTIC**: всё остальное

**Логика**: Иерархическая rule-based классификация (hard gates → soft rules)

**Критическая проблема**: Классификация основана на **статических паттернах**, а не на **runtime-тестах**. Это означает:
- ✅ Быстро и автоматически
- ❌ Может пропустить runtime-проблемы
- ❌ Не проверяет фактическую детерминированность на длинной дистанции

#### 2.4. Scoring система (`score()`)

**Роль**: Вычисление численного score для ранжирования вариантов

**Формула (текущая)**:
```javascript
score = Σ(feature_present * weight)
```

**Версионирование**: `master/scoring.json` (v2.0.0) → `master/scoring_v2.json` (v2.1.0, предложение)

**Эволюция**:
- **v2.0.0**: Ручные веса на основе экспертных знаний
- **v2.1.0** (предложение): `score = Σ(feature_present * log(lift + 1) * confidence_weight * manual_weight)`

**Сильные стороны**:
- ✅ Версионирование весов
- ✅ Интеграция статистического анализа (Lift) в v2.1.0
- ✅ Логарифмирование для сглаживания экстремальных значений

**Слабые стороны**:
- ⚠️ Score не отражает runtime-качество (только статические признаки)
- ⚠️ Нет нормализации по количеству признаков (вариант с большим количеством фич получает больший score)

#### 2.5. Статистический анализатор (`scripts/feature-diff.mjs`)

**Роль**: Вычисление корреляций между признаками и классом STABLE

**Метрика**: **Lift** = `P(feature|STABLE) / P(feature|OTHER)`

**Результат**: `master/feature_diff_stable_vs_other.json`
- `top`: Топ-25 признаков с высоким Lift (характерны для STABLE)
- `bottom`: Топ-25 признаков с низким Lift (не характерны для STABLE)

**Ключевые находки**:
- `has_fixed_timestep`: Lift=999 (абсолютный gatekeeper)
- `has_accumulator_loop`: Lift=64
- `force_noise_jitter`: Lift=4.57 (спорная фича)

**Сильные стороны**:
- ✅ Объективная метрика корреляции
- ✅ Фильтрация шума (coverage >= 3)
- ✅ Учет coverage для избежания переобучения на редких фичах

**Слабые стороны**:
- ⚠️ Малые данные (7 STABLE из 71) → статистика может быть шумной
- ⚠️ Lift не учитывает причинно-следственные связи (correlation ≠ causation)
- ⚠️ Нет проверки на мультиколлинеарность (признаки могут быть зависимы)

#### 2.6. Генератор промптов (`scripts/generate-prompt-constraints.mjs`)

**Роль**: Автоматическая генерация системного промпта для Gemini на основе статистического анализа

**Категории ограничений**:
1. **Hard Constraints** (Lift > 100): Обязательные требования
   - `has_fixed_timestep` → "You MUST use a fixed timestep approach..."
2. **Soft Hints** (2 < Lift <= 100): Рекомендации
   - `has_clusters`, `force_noise_jitter` → рекомендации с объяснениями
3. **Negative Constraints**: Явные запреты
   - `setState_in_raf`, `uses_date_now`, `uses_math_random` → анти-паттерны

**Результат**: `master/prompt_constraints.md`

**Сильные стороны**:
- ✅ Замыкание цикла обратной связи (feedback loop)
- ✅ Автоматизация prompt engineering
- ✅ Объяснимые ограничения (с описаниями)

**Слабые стороны**:
- ⚠️ Нет A/B тестирования эффективности промптов
- ⚠️ Нет версионирования промптов (только один файл)
- ⚠️ Нет метрик успешности (сколько STABLE вариантов после применения)

### Имплицитные архитектурные решения

1. **Статический анализ вместо runtime-тестов**: Быстро, но может пропустить проблемы
2. **Rule-based классификация**: Объяснимая, но может быть переобучена
3. **Run-based организация**: Изоляция экспериментов, но нет автоматического сравнения runs
4. **Версионирование scoring**: Контроль изменений, но нет автоматического rollback
5. **Маппинг промптов**: Отслеживание влияния промптов, но нет метрик эффективности

## 3. ОЦЕНКА ТЕХНИЧЕСКОГО КАЧЕСТВА

### Хорошо спроектированные части

#### 3.1. Run-based структура
- ✅ Четкая изоляция экспериментов
- ✅ Возможность отслеживания эволюции
- ✅ Нормализация структуры вариантов

#### 3.2. AST-анализатор
- ✅ Детальная детекция с логированием (feature_events)
- ✅ Комбинация regex + AST для баланса
- ✅ Обработка edge cases (игнорирование node_modules, поиск ключевых файлов)

#### 3.3. Версионирование scoring
- ✅ Контроль изменений весов
- ✅ Обоснование изменений (rationale)
- ✅ Предложения улучшений (scoring_v2.json)

#### 3.4. Статистический анализ
- ✅ Объективная метрика (Lift)
- ✅ Фильтрация шума (coverage >= 3)
- ✅ Учет confidence для спорных фич

### Хрупкие или переобученные части

#### 3.1. Классификация STABLE
**Проблема**: Основана на статических паттернах, не проверяет runtime

**Риски**:
- Вариант может иметь `has_fixed_timestep`, но использовать несидированный рандом в другом месте
- Вариант может быть помечен как STABLE, но иметь численную нестабильность на длинной дистанции
- Короткие тесты могут не выявить проблемы

**Пример**: `force_noise_jitter` с Lift=4.57 может использовать несидированный `Math.random()`, что приведет к недетерминированности на длинной дистанции, но статический анализ этого не обнаружит.

#### 3.2. Scoring формула
**Проблема**: Не нормализована по количеству признаков

**Риски**:
- Вариант с большим количеством фич получает больший score, даже если они не критичны
- Нет учета важности признаков (все веса суммируются линейно)

**Решение**: Использовать взвешенное среднее или нормализацию по количеству признаков

#### 3.3. Статистика на малых данных
**Проблема**: 7 STABLE из 71 (≈10%) → статистика может быть шумной

**Риски**:
- Один случайный успешный прогон с редким признаком может неоправданно задрать его вес
- Lift может быть переоценен из-за малой выборки

**Решение**: 
- Синтетическое увеличение STABLE вариантов (рефакторинг успешных)
- Bootstrap-анализ для оценки доверительных интервалов

### Чистая архитектура vs эмерджентная

#### Чистая архитектура
- ✅ Run-based структура (явное разделение экспериментов)
- ✅ Версионирование scoring (контроль изменений)
- ✅ Разделение ответственности (ingest → analyze → diff → generate)

#### Эмерджентная архитектура
- ⚠️ Классификация эволюционировала из простых правил в сложную иерархию
- ⚠️ Scoring эволюционировал от ручных весов к статистическим
- ⚠️ Нет явной модели данных (features определяются имплицитно через код анализа)

### Технический долг vs намеренное исследование

#### Технический долг
1. **Нет runtime-тестов**: Критично для валидации статического анализа
2. **Нет дедупликации по содержимому**: Варианты могут быть идентичными, но иметь разные имена
3. **Нет метрик эффективности промптов**: Неизвестно, улучшают ли новые промпты качество
4. **Нет автоматического сравнения runs**: Требуется ручной анализ

#### Намеренное исследование
1. **Статический анализ вместо runtime**: Быстро для итераций, но требует валидации
2. **Rule-based классификация**: Объяснимая, но может быть переобучена
3. **Малые данные**: Естественно для исследовательского проекта, но требует осторожности

## 4. АНАЛИЗ ОСНОВНОЙ ИДЕИ

### Что ново или интересно

#### 4.1. Статический анализ для оценки детерминированности
**Новизна**: Использование AST-анализа для предсказания runtime-поведения

**Интерес**: Может ли статический анализ заменить runtime-тесты для оценки детерминированности?

**Ограничения**: Статический анализ не может обнаружить:
- Численную нестабильность (floating-point errors)
- Проблемы на длинной дистанции (drift)
- Контекстные зависимости (например, порядок выполнения)

#### 4.2. Обратная связь через статистический анализ
**Новизна**: Использование Lift для автоматической генерации промптов

**Интерес**: Может ли статистический анализ корреляций улучшить prompt engineering?

**Ограничения**: 
- Correlation ≠ causation
- Малые данные → шумная статистика
- Переобучение на редких признаках

#### 4.3. Run-based организация для экспериментов
**Новизна**: Изоляция экспериментов с отслеживанием промптов

**Интерес**: Может ли run-based организация улучшить воспроизводимость экспериментов?

**Ограничения**: Нет автоматического сравнения runs, нет метрик эффективности

### Что измеряется или открывается

#### Измеряется
1. **Корреляция статических признаков с "стабильностью"**
   - Метрика: Lift = P(feature|STABLE) / P(feature|OTHER)
   - Результат: Топ-25 признаков, характерных для STABLE

2. **Эффективность промптов**
   - Метрика: Количество STABLE вариантов после применения промптов
   - Проблема: Нет автоматического отслеживания

3. **Качество вариантов**
   - Метрика: Score = Σ(feature_present * weight)
   - Проблема: Не отражает runtime-качество

#### Открывается
1. **Паттерны стабильности**: Какие статические паттерны коррелируют с детерминированностью?
2. **Анти-паттерны**: Какие паттерны гарантированно приводят к нестабильности?
3. **Эффективность prompt engineering**: Могут ли автоматически сгенерированные промпты улучшить качество?

### Статистическая/логическая обоснованность

#### Обоснованно
- ✅ Использование Lift для измерения корреляции
- ✅ Фильтрация шума (coverage >= 3)
- ✅ Логарифмирование для сглаживания экстремальных значений

#### Проблематично
- ⚠️ **Малые данные**: 7 STABLE из 71 → статистика может быть шумной
- ⚠️ **Correlation ≠ causation**: Высокий Lift не означает причинно-следственную связь
- ⚠️ **Мультиколлинеарность**: Признаки могут быть зависимы (например, `has_fixed_timestep` и `has_accumulator_loop`)
- ⚠️ **Переобучение**: Один случайный успешный прогон может неоправданно задрать вес редкого признака

### Предположения системы

1. **Статические паттерны коррелируют с runtime-поведением**
   - Предположение: Наличие `has_fixed_timestep` гарантирует детерминированность
   - Реальность: Может быть неверно, если есть другие источники недетерминированности

2. **Rule-based классификация достаточна**
   - Предположение: Иерархия правил покрывает все случаи
   - Реальность: Могут быть edge cases, не покрытые правилами

3. **Малые данные достаточны для статистики**
   - Предположение: 7 STABLE достаточно для надежной статистики
   - Реальность: Может быть недостаточно для надежных выводов

4. **Lift отражает важность признаков**
   - Предположение: Высокий Lift = важный признак
   - Реальность: Может быть переоценен из-за малой выборки

### Где может сломаться или дать ложную уверенность

#### Ложная уверенность
1. **Вариант помечен как STABLE, но недетерминирован на runtime**
   - Причина: Статический анализ не обнаружил скрытые источники недетерминированности
   - Пример: `force_noise_jitter` использует несидированный рандом

2. **Высокий Lift не означает важность признака**
   - Причина: Малые данные → шумная статистика
   - Пример: Редкий признак может иметь высокий Lift случайно

3. **Score не отражает runtime-качество**
   - Причина: Score основан на статических признаках
   - Пример: Вариант с высоким score может быть нестабильным на runtime

#### Где может сломаться
1. **Новые паттерны недетерминированности**
   - Проблема: Система не обнаружит новые анти-паттерны
   - Решение: Расширение AST-анализа, runtime-тесты

2. **Изменение определения STABLE**
   - Проблема: Классификация может быть переобучена на текущих данных
   - Решение: Валидация на новых данных, runtime-тесты

3. **Переобучение на редких признаках**
   - Проблема: Редкий признак может получить неоправданно высокий вес
   - Решение: Bootstrap-анализ, confidence intervals

## 5. НЕДОСТАЮЩИЕ КОМПОНЕНТЫ

### Для серьезного исследовательского инструмента

#### 5.1. Runtime-тесты для валидации статического анализа
**Что нужно**:
- Запуск вариантов с одинаковым seed
- Сравнение хэшей состояний на разных итерациях
- Обнаружение численной нестабильности (floating-point errors)

**Почему важно**: Статический анализ может пропустить runtime-проблемы

**Сложность**: Средняя (требует изоляции выполнения, управления seed)

#### 5.2. Метрики эффективности промптов
**Что нужно**:
- A/B тестирование промптов
- Отслеживание количества STABLE вариантов после применения промптов
- Сравнение runs с разными промптами

## 6. ОЦЕНКА ЛОГИКИ КЛАССИФИКАЦИИ

### Определение STABLE vs NON-STABLE

#### Текущее определение STABLE
```javascript
STABLE = has_fixed_timestep 
      && (uses_performance_now || has_deterministic_rng || has_stateRef)
      && !setState_in_raf
```

#### Проблемы определения

1. **Неполнота**: Не учитывает все источники недетерминированности
   - Пример: Вариант может иметь `has_fixed_timestep`, но использовать несидированный рандом в другом месте
   - Решение: Расширить проверки на все источники недетерминированности

2. **Избыточность**: Условие `uses_performance_now || has_deterministic_rng || has_stateRef` может быть избыточным
   - Пример: `has_stateRef` не гарантирует детерминированность
   - Решение: Уточнить условия (например, `has_stateRef` должен использоваться для mutable state, а не для детерминированности)

3. **Статичность**: Основано на статических паттернах, не проверяет runtime
   - Пример: Вариант может быть помечен как STABLE, но иметь численную нестабильность
   - Решение: Добавить runtime-тесты для валидации

### Разумность эвристик

#### Разумные эвристики
- ✅ `setState_in_raf` → INVALID (критическое нарушение производительности)
- ✅ `uses_date_now` → NON_DETERMINISTIC (не монотонное время)
- ✅ `!has_fixed_timestep` → NON_COMPLIANT (абсолютный gatekeeper)

#### Спорные эвристики
- ⚠️ `has_stateRef` → часть условия STABLE (может быть избыточным)
- ⚠️ `uses_performance_now` → часть условия STABLE (не гарантирует детерминированность)
- ⚠️ `force_noise_jitter` → не проверяется на детерминированность (может использовать несидированный рандом)

### Переобучение

#### Переобучение на текущих данных
**Проблема**: Классификация может быть переобучена на 7 STABLE вариантах

**Признаки переобучения**:
- Редкие признаки имеют высокий Lift (например, `force_noise_jitter` с Lift=4.57, но только 3 случая)
- Условия STABLE могут быть слишком специфичными для текущих данных

**Решение**:
- Валидация на новых данных
- Bootstrap-анализ для оценки устойчивости
- Упрощение условий (убрать избыточные проверки)

#### Недостаточная спецификация

**Проблема**: Некоторые условия недостаточно специфицированы

**Примеры**:
- `has_fixed_timestep`: Не проверяется, что timestep действительно фиксированный (может быть переменным)
- `has_deterministic_rng`: Не проверяется, что RNG используется везде, где нужен рандом
- `force_noise_jitter`: Не проверяется, что использует детерминированный RNG

**Решение**: Расширить AST-анализ для проверки контекста использования

### Что должно измеряться на runtime

#### 5.1. Детерминированность
**Что**: Запуск с одинаковым seed должен давать одинаковые результаты

**Метрика**: Хэш состояния на каждой итерации

**Почему важно**: Статический анализ не может гарантировать детерминированность

#### 5.2. Численная стабильность
**Что**: Отсутствие floating-point errors на длинной дистанции

**Метрика**: Отклонение от ожидаемого состояния

**Почему важно**: Даже детерминированный код может иметь численную нестабильность

#### 5.3. Производительность
**Что**: FPS, использование памяти

**Метрика**: Средний FPS, пиковое использование памяти

**Почему важно**: Стабильность ≠ производительность

#### 5.4. Визуальное качество
**Что**: Отсутствие артефактов, плавность анимации

**Метрика**: Субъективная оценка, автоматическое обнаружение артефактов

**Почему важно**: Стабильность ≠ визуальное качество

## 8. CORE THESIS (Основной тезис системы)

### Если эта система станет реальным продуктом или исследовательским фреймворком, каков будет её основной тезис?

**CORE THESIS**:

> **Статические паттерны кода можно использовать для предсказания детерминированности анимационных движков, генерируемых LLM, и автоматически улучшать промпты через статистический анализ корреляций.**

### Расширенная формулировка

Система утверждает, что:

1. **Детерминированность предсказуема статически**: Наличие определенных паттернов кода (например, `has_fixed_timestep`, `has_deterministic_rng`) коррелирует с фактической детерминированностью на runtime.

2. **Статистический анализ улучшает промпты**: Корреляции между признаками и "стабильностью" (измеряемая через Lift) могут быть использованы для автоматической генерации эффективных промптов.

3. **Обратная связь замыкает цикл**: Статический анализ → статистический анализ → генерация промптов → новая генерация → улучшение качества.

### Критические допущения тезиса

1. **Статические паттерны достаточны**: Статический анализ может заменить runtime-тесты для оценки детерминированности.
   - **Проблема**: Может быть неверно для численной нестабильности, скрытых источников недетерминированности
   - **Требует валидации**: Runtime-тесты для проверки

2. **Корреляция отражает причинность**: Высокий Lift означает важность признака.
   - **Проблема**: Correlation ≠ causation, малые данные → шумная статистика
   - **Требует валидации**: Bootstrap-анализ, больше данных

3. **Автоматические промпты эффективны**: Автоматически сгенерированные промпты улучшают качество.
   - **Проблема**: Нет метрик эффективности промптов
   - **Требует валидации**: A/B тестирование промптов

### Если тезис верен, что это означает?

- ✅ Можно автоматизировать prompt engineering для генерации детерминированных движков
- ✅ Статический анализ может заменить дорогие runtime-тесты
- ✅ Система может масштабироваться на большие объемы данных

### Если тезис неверен, что это означает?

- ❌ Статический анализ недостаточен → нужны runtime-тесты
- ❌ Корреляции не отражают причинность → нужен причинно-следственный анализ
- ❌ Автоматические промпты неэффективны → нужен ручной prompt engineering

### Что нужно для валидации тезиса?

1. **Runtime-тесты**: Валидация того, что статический анализ корректно предсказывает детерминированность
2. **Метрики эффективности промптов**: Проверка того, что автоматические промпты улучшают качество
3. **Больше данных**: Увеличение выборки STABLE для более надежной статистики
4. **Bootstrap-анализ**: Оценка неопределенности из-за малых данных
